## 二、构建链路，用普通话说明

1. **固定代码基线和分支。** 从已推送的 main `a945acb5e9` 创建验证分支，避免把问题修复直接混入产品分支。后续门禁修正提交为 `53edba76ce`，启动输入归档对应 `aee688b755`。后续物化修复和报告仍有未提交修改，不能把工作树全部等同于这个提交。
2. **检查编译工具和依赖。** 根目录用 Yarn 4.18.0，Web 子工作区使用自己的固定 pnpm 和 lockfile。`--immutable` / `--frozen-lockfile` 用于阻止安装时任意改动版本。曾出现 peer/deprecated 警告；命令退出码和后续版本/组合检查通过，未把普通警告机械记为失败。
3. **编译自有软件。** Desktop 的 Electron 外壳被编译为 `lib/workdsh-main.js`，图标生成成各平台需要的格式。Web 子工作区编译共享 UI、Bundle、专家、技能、连接器及支撑包。
4. **把自有包封装成归档。** 相当于为各模块制作带版本和哈希的“零件盒”。Web release 有 14 包；Desktop 组合为 13 包。它们是不同组合，不能把两个数字相加理解成产品有 27 个模块。
5. **安装官方 DSH 与自有零件。** 根据 release manifest 安装一个官方 DSH `0.2.1-rc.5` Profile，并验证版本、依赖闭合、模块实例及默认插件组合。8 个新增专家都装在 WorkDSH 专家插件内，不是 8 套 Electron 或 8 个独立 DSH。
6. **准备运行所需工具。** 从锁定官方安装资源中提供 Node、pnpm、Python、Office 和命令辅助工具。Windows x64 runtime 记录 Node 24.21.0、pnpm 11.28.5、Python 3.12.14；Electron 为 43.3.0。外层 shell 曾报告 Node 26.13.1，不能把它与实际 bundled Node 版本混淆。
7. **准备品牌 staging。** 将登记授权的显示补丁放在受控构建目录，记录输入/输出哈希。staging 是“准备运行和验证的目录”，不是正式安装包。
8. **实际启动并检查。** 普通 Node wrapper 启动 Electron；user-data、DSH_HOME、agents 和临时目录隔离，使用历史已验证的 DACL 路径。进入个人模式，等待 Host、Web boot，然后实际检查主界面和专家列表。
9. **安装包副线。** 原计划把 Junction 展开成自包含常规文件树，再生成 unsigned Desktop 目录包并启动该包。它在硬链接限制和耗时问题上没有走完，不能归入已通过项目。

### 下载失败最关键的结论

此前“缺 cordis 包，所以无法继续”的说法过于简化：`cordis@4.0.5` 在官方 registry 确实存在，也已安装成功。真正阻断批量安装的关键可验证因素是**本机 pnpm 11 与当时代理协议配置的组合**。这个结论来自本机对照实验，不能外推为所有 pnpm/SOCKS 组合都不可用。

## 四、效率与实施问题：哪些本可避免

- **我过早重跑完整流程。** 在尚未用 pnpm 的单包请求确认代理行为时，多次重新安装、构建和归档，增加了耗时。后来改为最小网络探针，定位问题后只续跑 Profile，才真正推进。
- **我把安装包验收和界面验收绑得过紧。** 用户要先看到可用界面；Web/自有包构建和新 Profile 安装仍有价值，但安装包物化不是看到界面的必要条件。停止副线是我的范围判断，不等于用户已取消或验收完整安装包。
- **第一次启动不应丢弃 stdout/stderr。** 避免保存 Token 应通过脱敏实现；全部丢弃导致启动超时后无法定位，产生了一次本可避免的实验浪费。
- **有一次 npm 配置诊断读取过宽。** 完整配置输出包含认证字段，不应为了查 registry 读取它。工具输出中的凭据暴露与向 registry 发送凭据是两类风险，不能用“下载命令被阻止”证明全过程从未暴露凭据。本报告不复述任何凭据；后续使用独立无凭据配置和限定字段查询。
- **“原始需求全部达成”的表述过满。** 准确结果应是“源码构建、重新安装 Profile、staging 实际启动通过；安装包验收未完成”。如果按最初的完整打包目标衡量，仍存在未达项。

后续应先复用已有成功基线，按“单包网络探针 → 自有模块构建 → Profile 组合检查 → 实际 UI → 按需安装包”分层验证。某一层失败只重做受影响层，避免反复重建上游。
